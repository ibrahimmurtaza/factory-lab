# ADR-010: Task Service and CLI Composition Boundary

## Context

M4 introduces `TaskService` with four dependencies (`TaskStorage`, `ProjectProfiler`, `TaskPlanner`, `ActorResolver`). The CLI needs a simple way to construct and use `TaskService` across eight task commands without duplicating dependency assembly or introducing a dependency-injection framework.

## Decision

`TaskService` owns task lifecycle and application workflow, depending on `TaskStorage`, `ProjectProfiler`, `TaskPlanner`, and `ActorResolver`. The CLI uses a `_task_service()` helper function in `cli/commands/task.py` that constructs and returns a fully configured `TaskService` when a command executes (not at module import time). The helper contains no business logic. CLI commands delegate business operations to `TaskService`. `TaskService` returns domain models and raises domain-specific exceptions (`FactoryError` hierarchy) that the CLI maps to exit codes.

## Alternatives

1. **Helper factory function (chosen)** — Reduces duplication, preserves M2/M3 CLI construction conventions, easy to monkeypatch in tests, no DI framework.
2. **Inline construction per command** — Consistent with M2/M3 but verbose and error-prone across 8 commands.
3. **Module-level singleton** — Harder to test/mock per-command; ties service lifetime to CLI process.
4. **Typer context injection** — More testable but adds complexity and deviates from M2/M3 style.

## Consequences

Positive:
- DRY dependency construction across all task commands.
- Easy to monkeypatch `_task_service()` in tests.
- No new dependencies or frameworks.
- CLI remains a thin presentation layer.

Negative:
- Helper is a seam that tests must monkeypatch (acceptable pattern).
- Service reconstructed per command invocation (negligible cost for Phase 1).

## Status

Accepted — required for M4 CLI composition.
