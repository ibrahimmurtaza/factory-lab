# ADR-006: Task Persistence and Storage Abstraction

## Context

M4 requires durable task state that survives separate CLI invocations. M7 defers database introduction, so M4 needs a file-based persistence strategy that is replaceable by a database implementation later. The existing M2 configuration storage uses `~/.factory-lab/config.json` with atomic writes via a `ConfigStorage` protocol; M4 should follow the same pattern for tasks.

## Decision

Task state is persisted as one JSON sidecar file per task under `~/.factory-lab/tasks/<task-id>.json`. A `TaskStorage` protocol defines `load`, `save`, and `list_all`. `JsonTaskStorage` implements it with atomic writes (temporary file + `os.replace`), schema versioning, and JSON serialization. The storage layer is independent of the `TaskRecord` domain model so a future database implementation can replace it at M7 without changing `TaskService`.

## Alternatives

1. **JSON sidecar files per task (chosen)** — Simple, no new dependencies, follows existing M2 config pattern, human-inspectable, atomic writes prevent corruption, easy to replace with a database later.
2. **Single JSON task registry file** — Risk of concurrent-write corruption; harder to scale; single point of failure for all tasks.
3. **SQLite database (deferred to M7)** — Premature infrastructure per AGENTS.md and ARCHITECTURE.md; adds operational complexity before justified.
4. **In-memory only** — Task state lost on process exit; violates requirement that `factory task status` works across CLI invocations.

## Consequences

Positive:
- Immediate local durability with no infrastructure setup.
- Database migration at M7 is a storage-layer implementation, not an architectural rewrite.
- Atomic writes prevent partially written task records.
- Follows the established `ConfigStorage`/`JsonConfigStorage` pattern from M2.

Negative:
- File enumeration for `list_all()` is less efficient than a database query (acceptable for Phase 1 scale).
- Schema migration logic must be added when moving to a database at M7.

## Status

Accepted — required for M4 task persistence.
