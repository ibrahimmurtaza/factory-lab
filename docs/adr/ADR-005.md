# ADR-005: Replaceable coding runtime and model provider adapters

## Context

OpenCode is the initial coding runtime and OpenRouter is the initial model provider, but both must be interchangeable so other runtimes (e.g., Aider, custom agents) and model providers can be integrated later without changing orchestration logic.

## Decision

Coding runtimes and model providers are implemented as adapters behind interfaces (`CodingRuntime` and `ModelProvider`). OpenCode and OpenRouter are the Phase 1 implementations. Orchestration depends only on the interfaces, not on OpenCode- or OpenRouter-specific types.

## Alternatives

1. **Adapter interfaces (chosen)** — Enables runtime/provider substitution; small upfront cost; aligns with runtime/provider independence principles.
2. **Direct OpenCode/OpenRouter imports in orchestration** — Simplest for Phase 1 but couples the core to specific tools; contradicts runtime/provider independence.
3. **Abstraction framework (e.g., LangGraph) for orchestration** — Deferred; not justified until orchestration complexity requires stateful graph-based flows.

## Consequences

Positive:
- OpenCode and OpenRouter can be swapped without touching orchestration.
- Future runtimes/providers added by implementing the interface.
- Control plane remains free of vendor-specific dependencies.

Negative:
- Interface design must anticipate enough of each runtime's capability surface to avoid frequent redesign.
- No second implementation exists yet, so the interface is speculative; keep it minimal per "no premature abstractions."

## Status

Accepted — confirmed architectural principle; interface kept minimal until a second implementation is concrete.
