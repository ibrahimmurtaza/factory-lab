# ADR-013: Git Worktree Isolation and Execution Workspace

## Context

Execution must not pollute the user's registered repository working tree. ADR-001 (local-first/cloud-capable) and ADR-003 (control/execution separation) support incremental isolation: workspaces → worktrees → containers → cloud workers. Changes must never be automatically merged into the original branch. M7 defers Docker/container execution, so M5 uses Git worktrees.

## Decision

Create one Git worktree per execution attempt, named `factory-lab-<task-id>-<attempt>`, adjacent to the registered repository. The worktree is retained after execution (success or failure) until the user explicitly acknowledges delivery or runs cleanup. Factory Lab never auto-merges worktree changes into the original branch. Worktree isolation organizes Git working directories but is not a filesystem security sandbox.

## Alternatives

1. **Execute directly in the registered repository (rejected)** — Risks polluting the working tree and complicates undo/rollback.
2. **Auto-merge completed work into the original branch (rejected)** — Violates the "never auto-merge" principle; removes human review before delivery.
3. **OS-level sandboxing of the worktree (deferred)** — Worktree isolation is not a security boundary; sandboxing is a later security milestone (see ADR-014).

## Consequences

Positive:

- Clean isolation per attempt; failed work can be inspected before cleanup.
- Easy rollback: delete the worktree, original repo untouched.
- Matches the ADR-001 isolation progression (workspaces → worktrees → containers).

Negative:

- Worktrees accumulate on disk until manually cleaned.
- Git surface area increases (worktree management commands).

## Status

Accepted — M5 execution workspace model.
