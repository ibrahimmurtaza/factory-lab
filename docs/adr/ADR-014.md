# ADR-014: Execution Approval and Security Boundaries

## Context

AGENTS.md and ARCHITECTURE.md require approval gates for sensitive operations (file writes outside workspace, destructive Git, network commands, code delivery). OpenCode runs as an autonomous subprocess; prompt instructions alone are not sufficient security boundaries. Secrets must never be logged. Worktree isolation (ADR-013) is not a sandbox.

## Decision

Enforce pre-dispatch, operation-specific human approval for sensitive operations: dependency installation, network-dependent commands, destructive Git operations, and writes outside approved `affected_components`. Approval applies only to the identified operation and execution attempt; unanticipated sensitive operations are denied, not silently permitted. Use an explicit environment-variable allowlist for the OpenCode subprocess (not inheriting the full caller environment) and redact secret-like values from captured stdout/stderr before logging. No OS-level sandboxing in M5; scope violations are detected via diff review against `affected_components`, not technically prevented.

## Alternatives

1. **Runtime pause/resume interactive approval (rejected)** — Requires unconfirmed OpenCode protocol support; stdout/stderr capture is observability, not enforcement.
2. **Inherit full caller environment (rejected)** — Exposes unrelated credentials, cloud tokens, and secrets to the runtime.
3. **OS-level sandboxing in M5 (rejected)** — Deferred to a later security milestone; worktree isolation is not a sandbox.

## Consequences

Positive:

- Approval is explicit, operation-specific, and recorded; no blanket step permission.
- Secrets are allowlisted and redacted; never written to execution logs.
- Enforcement lives outside the OpenCode prompt, in Factory Lab's dispatch layer.

Negative:

- Pre-dispatch approval adds user friction per sensitive operation.
- Out-of-scope writes are not technically blocked; detected post-hoc via diff review.

## Status

Accepted — M5 approval and security model.
