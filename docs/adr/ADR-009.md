# ADR-009: Actor Attribution and Identity Resolution

## Context

M4 records who approved or rejected a plan (`ApprovalRecord.actor`) and who triggered lifecycle transitions (`LifecycleEvent.actor`). No authentication or authorization infrastructure exists in Phase 1. A lightweight, replaceable actor resolution mechanism is needed for attribution without introducing user accounts, passwords, or auth systems.

## Decision

`ActorResolver` resolves the actor in this order: (1) `FACTORY_LAB_ACTOR` environment variable, (2) fall back to `getpass.getuser()`. Whitespace is trimmed; empty values are rejected with a clear error. If no valid actor can be resolved, `ActorResolutionError` is raised before recording an anonymous approval or rejection. `TaskService` resolves the actor internally; no CLI `--actor` flag. This mechanism provides attribution, not verified authentication or authorization.

## Alternatives

1. **Environment variable with OS-user fallback (chosen)** — Simple, configurable, no CLI friction, replaceable for future identity integration.
2. **CLI `--actor` flag** — Explicit but adds friction to every approval/rejection; deviates from thin CLI principle.
3. **Hardcoded "operator" default** — No attribution value; meaningless in multi-user environments.
4. **Full authentication system (deferred)** — Premature infrastructure; no multi-user requirement in Phase 1.

## Consequences

Positive:
- Attribution for all approval/rejection/cancellation decisions.
- Configurable via environment without code changes.
- No authentication infrastructure to maintain in Phase 1.
- Replaceable when proper identity integration is added.

Negative:
- Actor is not verified; shared environments may have ambiguous attribution.
- Documented limitation: attribution, not authentication.

## Status

Accepted — required for M4 actor attribution.
