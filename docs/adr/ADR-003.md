# ADR-003: Control plane and execution plane separation

## Context

Orchestration (deciding what to do) must be separated from execution (performing file/terminal/Git operations) so the framework can support multiple runtimes, isolated workspaces, and eventual cloud workers without leaking execution details into planning logic.

## Decision

Factory Lab is split into a control plane and an execution plane communicating through interfaces. The control plane handles orchestration, task management, project management, agent coordination, model configuration, and execution tracking. The execution plane handles repository operations, file modifications, terminal commands, testing, builds, and Git operations. Orchestration never imports execution-plane internals directly.

## Alternatives

1. **Layered monolith, no boundary** — Simpler initially but couples planning to execution; prevents isolated/cloud execution.
2. **Separate services with network boundary** — Premature infrastructure; adds operational complexity before justified.
3. **Interface boundary within a modular monolith (chosen)** — Clear separation without network overhead; services can later be split if needed.

## Consequences

Positive:
- Execution can move to Docker/cloud workers by implementing the execution-plane interface.
- Control plane is testable with mocked execution.
- Multiple coding runtimes can be supported through the same boundary.

Negative:
- Requires discipline to keep the boundary clean as code grows.
- Indirection for calls that today are local and direct.

## Status

Accepted — confirmed architectural principle.
