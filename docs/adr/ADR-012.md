# ADR-012: Coding Runtime and Execution Environment

## Context

OpenCode is the initial coding runtime but Factory Lab must not couple to it. ADR-005 mandates replaceable runtime adapters behind an interface; ADR-003 requires the control plane never imports execution-plane internals. OpenCode's structured event protocol is unconfirmed. No OpenCode adapter or execution plane exists yet; M5 builds both.

## Decision

Define a `CodingRuntime` interface in the control plane and implement an OpenCode adapter that invokes OpenCode as a subprocess CLI, passing the approved plan step via stdin/args and capturing opaque stdout/stderr plus exit code. Define a minimal `ExecutionEnvironment` interface with a local-process implementation in M5 to keep the cloud-worker path open without building cloud infrastructure. The adapter returns a structured `ExecutionResult` built from exit code, stdout, stderr, and observed artifacts — not from unconfirmed OpenCode event types. Orchestration depends only on the `CodingRuntime` interface; no OpenCode imports enter the control plane.

## Alternatives

1. **Direct OpenCode imports in orchestration (rejected)** — Violates ADR-003 and ADR-005; couples the control plane to a specific runtime.
2. **Structured JSONL event parsing from OpenCode (rejected for M5)** — Depends on an unconfirmed OpenCode protocol; opaque output plus exit code is safer for M5.
3. **Network-bound runtime interface from day one (rejected)** — Premature; local-process is the only concrete implementation.

## Consequences

Positive:

- OpenCode is replaceable; orchestration depends only on the `CodingRuntime` interface.
- Cloud-worker migration later is an interface implementation, not a rewrite.
- No dependency on unconfirmed OpenCode structured output.

Negative:

- Result extraction from opaque output is heuristic in M5.
- Interface is speculative until a second runtime exists (mitigated by keeping it minimal).

## Status

Accepted — M5 runtime adapter foundation.
