# ADR-007: Task Lifecycle, Plan Revisions, and Approval Workflow

## Context

M4 introduces task intake and human approval of implementation plans. Execution is deferred to M5, so approval in M4 authorizes a plan as the basis for future implementation — it does not execute code. The system needs a lifecycle model with valid state transitions, immutable plan revision history, and explicit approval/rejection semantics distinct from cancellation.

## Decision

Task lifecycle states: `created`, `planning`, `awaiting_approval`, `approved`, `rejected`, `cancelled`, `failed`. Valid transitions: `created` → `planning` → `awaiting_approval` → `approved` or `rejected`; `rejected` → replan → `awaiting_approval`; `awaiting_approval` → `cancelled`; `approved` → replan → `awaiting_approval` (previous revision becomes `superseded`). `cancelled` and `failed` are terminal.

Plan revisions are sequential integers starting at 1, embedded in the task record. Revisions are immutable: replanning appends a new revision; rejected revisions remain `rejected`; approved revisions become `superseded` when materially replaced, retaining their original `ApprovalRecord`. A new revision always starts as `awaiting_approval`. Approval belongs to the individual `PlanRevision`.

## Alternatives

1. **Sequential revisions with immutable history (chosen)** — Simple, auditable, preserves historical approvals, no separate revision files.
2. **Mutable current plan only** — Loses historical context and approval decisions; cannot answer "what changed between revisions?"
3. **Separate revision directory per task** — More complex file management; no benefit over embedded revisions for Phase 1 scale.
4. **Approval at task level only** — Loses per-revision approval history; cannot track which revision was approved/rejected.

## Consequences

Positive:
- Complete audit trail of plan changes and approval decisions.
- Rejected plans can be replanned without losing history.
- Approved plans can be materially replaced with fresh approval required.
- Clear distinction between rejection (plan not accepted, replan allowed) and cancellation (task terminated).

Negative:
- Task records grow with each replan (acceptable for Phase 1).
- Consistency between task status and current revision status must be enforced by `TaskService`.

## Status

Accepted — required for M4 task lifecycle and approval workflow.
